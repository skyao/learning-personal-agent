我们用 OpenAI Dots 处理了一天真实的代理公司工作，然后查阅了 OpenAI 的文档和早期测试情况。Dots 如何运作、在哪里出了问题、应该先尝试什么。

## 第一部分：我们和 Dots 的第一天

我给我的 Dot 起名叫 Toby，并把我手上已有的工作交给它：日历冲突、客户跟进、Slack 对话和 SEO 监控。取得的有用进展足以让人明白为什么一个始终在线的助手可能很有价值；遇到的阻力也足以让当前的局限难以忽视。

### 有用的部分很早就出现了

Toby 第一次浏览我已连接的 Slack 和日历时，就找出了值得注意的事情。它发现了周一一场涉及预算外工作的客户讨论和一处日程重叠，接着又找到了周三的另一个会议冲突。这是个有希望的开端，因为它把不同地方的信息联系了起来，而不需要我先把所有东西粘贴到聊天里。

我让它帮忙把一场客户会议挪到下周，并跟进一份电子表格。Toby 注意到这份电子表格似乎是只读的，这可能导致客户无法进行我们希望他们做的编辑。我们仍需核实发给客户的究竟是哪个文件，所以这是一个有用的提醒，而不是一个确认的诊断。这正是助手应该发现的那类细节，前提是它要说清楚自己知道什么、还有什么需要核实。

在电子邮件上，进展停滞了。Toby 以为我用的是 Gmail，而我的配置是 Zoho 加上 Apple Mail 和 Outlook。一个设置小部件失败了，接着它给出了三个格式错误的链接，最后才提供了一个目录链接。我的 Mac 是在线的，但 Toby 没有获得在上面运行任务的授权，电子邮件和改期都没有完成。

我也提出了让助手广泛访问个人信息的顾虑。对于这项任务，我选择了让它写一份草稿，由我复制粘贴；我们还讨论了为 Toby 单独开一个邮箱作为下一步。那个邮箱仍停留在计划阶段。安全边界是合理的；错误的邮箱假设和反复出现的错误链接则是本可避免的失误，让一个简单的请求变得更难完成。

### Slack 带来了笑料，也带来了另一次现实检验

把 Toby 连接到 Slack 是成功的，它的显示名称变成了 Toby。不过，它在确认自己能否发送我想要的私信之前，就先宣布了连接成功。尝试给一位同事发的消息失败了，因为它所用的途径不支持那个目的地。通过一条明确的途径发到我们的群组，最终成功了，但宣布比证据来得更早。

Toby 加入群组后，团队给了它你能想到的那种欢迎。我的联合创始人 Tom 开玩笑地向它要我五年的报税资料。没有任何税务信息被分享出去。然后我让 Toby 给 Tom 回一句粗鲁的两个词，它一字不差地发了出去，注明来自我，然后介绍自己是我的新助手。被问到生日时，Toby 说它是今天被创建的。它的第一天，起哄比入职培训还多，但至少它见过团队了。

参与群组和跟上群组是两回事。一位同事在太平洋时间下午 4:24 左右请它做一份 PDF 摘要。Toby 直到 5:13 左右才接到这个请求，摘要在 5:15 左右送达。当人们期待对话中的某个人回应时，大约五十分钟是很长的等待。

我授权 Toby 在限定范围内处理日常的群组对话和非敏感的工作协助。这确立了它被允许做什么，但并不能证明今后每一次提及都会传达到它，并触发及时的回应。我们看到了它撰写并发送回答。我们还没有确认它能可靠地注意到什么时候需要回答。

### SEO 取得了具体进展

SEO 监控走得更远。我希望 Toby 关注两个客户网站，一家律师事务所和一家医疗诊所，留意趋势、机会和合格的潜在客户。第一条途径是通过 GSC Wizard，但因为账户没有有效订阅而失败了。那是账户层面的限制，所以重复请求也解决不了问题。

我让 Toby 改用浏览器。在完成安全的 Google 登录和设备批准之后，它确认了能访问客户的 Google Analytics 4 和 Search Console 数据。这是有意义的进展：它接触到了这项工作所需的实际工具和数据。

我们安排了一份合并的每日报告，每天太平洋时间上午 8 点左右发到我的私人 Slack，从第二天开始。计划包括 7 天和 28 天的对比，发现的情况在作为机会呈现之前要先经过核实。会话结束时，报告还没有运行，也没有送达。我们在设置上取得了进展，但可靠的报告和任何业务影响仍有待证明。目前还没有依据宣称 SEO 结果有所改善。

### 连接我们自己的工具比应有的更难

我把我们自己的 SEO 监控服务提供给 Toby，我们通过 MCP 把它连接到助手。MCP 是让助手使用另一项服务所提供工具的标准。这似乎是一种实用的方式，让 Toby 能接触到我们已有基础设施支持的工作，但连接它成了那个下午最令人沮丧的部分之一。

最初的配置指向一个本地 Node 进程，它无法在 Toby 的云端环境中运行，于是我们改用一个托管的端点。随后 Toby 反复让我在桌面端 MCP 配置和网页端插件设置之间来回切换，却没有讲清楚当前对话需要的是哪一个。一张截图显示桌面端的连接已经安装，但那并不是我们想用的托管网页插件。

有一刻我说：「这比应有的更难。」我还问：「这不就违背了有一个可以吩咐做事的助手的初衷吗？」这两个问题很好地概括了我的沮丧。我想要的是把工作完成的帮助，而 Toby 给我的下一件事，太常常是又一个需要我自己处理的排查步骤。

托管连接最终成功并完成了认证。然而，当服务器新增了工具时，对话里显示的仍是旧的工具集。重新安装插件刷新了可用工具，而不需要我关掉 Toby。这解决了不一致的问题，所以不应把它理解为该产品永远无法使用这些工具的证据。

连接正常后，Toby 创建了两个受监控的网站，并完成了抓取：律师事务所 44 个页面，医疗诊所 111 个页面。这些都是已完成的任务，尽管网站状态仍显示为待处理。Google 数据导入也被跳过了，因为服务器上没有配置任何 Google 连接。

最后这个细节很重要：在浏览器中登录 Google，并没有同时把 Google 的 API 连接到我们的 SEO 服务。Toby 进入了该服务的仪表盘，但连接表单要求提供凭证，而不是提供一个简单的 Google 登录按钮。这一步留给了我，也没有保存任何分析 API 连接。因此，我们的报告方式仍然依赖浏览器可访问的 Google 数据，加上抓取数据。

### 这一天结束时

当 Toby 拥有可用的访问权限和明确的任务时，它做得最好。它找到了相关的上下文，参与了 Slack 讨论，总结了一份文档，接触到了分析数据，并运行了网站抓取。在评估这次体验时，未完成的工作同样重要：会议和邮件任务没有完成，Slack 中的及时回应没有保证，第一份计划中的 SEO 报告也还没到时间。

我主要的批评是设置和状态需要太多的监督。有些障碍来自服务限制或正当的安全检查点。另一些则来自错误的假设、过早的确认和不清晰的指示。一个有用的助手需要能区分这些情况，对它能够自行恢复的问题负起责任，并准确说明发生了什么，以便用户决定下一步怎么做。

## 第二部分：根据文档和其他测试者，OpenAI Dots 如何运作

在查看了 Dots 的构建方式之后，我们那个下午的经历就更好理解了。没有授权的 Mac、无法在云端运行的本地工具，以及对任务应在哪里进行的困惑，都涉及同一个根本问题：一个 Dot 可以在多个环境之间协调工作，而每个环境都有自己的访问权限和限制。

### Dot 是一个协调者，而不是一台计算机

每个 Dot 都有自己的云端计算机和浏览器，连接你授权的应用，并同时保持多个项目的上下文。OpenAI 的帮助文档补充了一个重要细节：Dot 自己的计算机只是它的工作可以运行的地方之一。Dot 还可以：

- 创建单独的 ChatGPT Work 或 Codex 任务。
- 在你已在 Codex 中设置好的 Codex 云端环境中运行云端任务。
- 在你已连接的本地计算机上工作，这些任务会单独显示在侧边栏中。
- 当它的云端浏览器被某个网站拦截时，使用你的本地浏览器。

你可以在 Dot 的资料页中跟踪这些活动，资料页把工作分为 **进行中**、**已计划** 和 **已完成**。已计划的工作包括提醒和定期检查，比如我们设置的每日 SEO 报告。

OpenAI 的 GPT-6 Astra 系统卡把 Dots 描述为「常常把工作委派给子智能体」，并解释说多智能体配置和持久性并不新鲜。新的要素是一个时间预算设置，用来引导一个 Dot 在某件事上持续工作多长时间。综合来看，这些细节描述的是这样一个智能体：它掌握目标，并把工作的各个部分分配给它自己的计算机、Codex、子智能体或你的机器，而不是把所有东西都放在一台虚拟机上的一个 AI 进程里。

来源：[OpenAI 帮助：开始使用你的 dot](https://help.openai.com/en/articles/20001530-getting-started-with-your-dot)，[GPT-6 Astra 系统卡](https://deploymentsafety.openai.com/gpt-6-astra/evaluating-auto-review)。

### OpenAI Dots 的云端计算机有实际限制

云端计算机并不是一台不受限制的服务器，这有助于解释为什么我们基于 Node 的本地工具无法直接在那里运行。OpenAI 开发者论坛上的一位开发者在 Dot 的云端计算机上测试了一个 .NET 10 应用，完成了一部分：依赖项还原成功，后端编译通过，193 个后端测试通过。然而，完整的技术栈无法运行。环境是没有 sudo 的 Debian 13，Docker 已安装但无法访问宿主机的套接字，而无 root 的 Docker 也因为缺少所需权限而失败。

OpenAI 的工作区文档还补充了另一个对企业使用很重要的限制。Dot 的云端计算机不会继承成员的 VPN、浏览器登录状态或设备策略。如果某个内部工具或网站需要你的网络或登录，默认情况下就无法访问。我们自己也遇到了这种情况：Toby 需要自己完成 Google 登录和设备批准，才能进入 GA4 和 Search Console。

云端计算机适合浏览、文档、脚本、测试和代码修改。需要容器、特权访问、内部服务器或 VPN 的工作，需要另一个环境，比如一台已连接的本地计算机、一个 Codex 环境或一套定制系统。事先了解这一点，就更容易选择 Dot 在其可用环境中真正能够完成的任务。

来源：[OpenAI 开发者社区：dots 的 Docker 支持](https://community.openai.com/t/docker-container-support-for-dots-working-in-the-cloud-computers/1402440)。

### 连接本地计算机

本地计算机访问是可选的，并且默认关闭，这就是为什么我的 Mac 在线还不够。你需要在那台计算机上通过 ChatGPT 桌面应用连接它并确认访问。连接之后，Dot 就可以从它的任一消息渠道处理那台计算机上的文件并在上面运行命令，你也可以随时撤销这一访问。

这台计算机必须保持在线，并保持 ChatGPT 应用打开。在 Enterprise 工作区中，本地访问默认关闭，必须由管理员允许。这让两个环境承担不同的角色：云端计算机始终可供 Dot 使用，而你自己的计算机提供云端计算机所没有的文件、工具、网络和登录状态。

来源：[OpenAI 帮助：在 ChatGPT 工作区中管理 dots](https://help.openai.com/en/articles/20001554-manage-dots-in-chatgpt-workspaces)。

### 一位早期测试者的报告

迄今为止最详细的外部记述，来自一篇 [Reddit 帖子](https://www.reddit.com/r/OpenAI/comments/1wuznlr/i_spent_a_day_poking_dots_with_sticks_heres_what/)，发帖用户花了一天时间，让一个 Dot 去做超出 OpenAI 示例的事情。以下行为都没有在 OpenAI 的文档中记载，但该用户报告的几件事有助于说明其潜力：

- **工作并行运行。** Dot 在自己的计算机上继续工作，同时把一项任务发送到一台已连接的 Linux 机器，并运行一个单独的研究进程。
- **一个长项目保持了状态。** 一项涵盖数百份 PDF 的文档审阅运行了很长时间，期间用户问了一些无关的问题，还启动了其他任务。
- **一个受阻的步骤没有让项目停下来。** 当增加更多审阅者需要批准时，Dot 继续完成它已获准做的那些部分。
- **中断没有让它重置。** 在项目进行中被问到一个相关问题时，Dot 暂停下来，进行调查，更新了自己的理解，然后回到原来的工作上。
- **没有可见的任务队列。** Dot 似乎记得待处理的工作，检查某个环境是否已变得可用，并在稍后重试。

最后一点值得注意。传统的自动化使用显式的基础设施来处理队列、重试和调度。一个通过推理待处理工作来承担这些职责的 Dot 提供了更大的灵活性，但也更难审计。当你发现自己在问某件事是否真的完成了的时候，我们自己的这一天就表明了这会多快变成一个实际问题。

### 为什么编排才是真正的功能

想想准备一份重要的客户方案需要做些什么。你可能需要审阅客户的材料、研究行业、阅读一份旧方案、检查技术要求、向开发团队提一个问题、构建一个概念验证、更新定价，并在需求变化时修改所有内容。每项任务单独来看都可以应付。让整个项目持续推进，则需要协调。

你已经可以用 ChatGPT 完成其中的每一步。打开十个聊天，每个分配一项任务，你会得到十个有用的回答，但**你自己成了编排层**。你必须记住哪个聊天知道什么、在对话之间搬运发现、跟踪未完成的工作、重启失败的任务，并决定下一步做什么。

Dot 承担了这种协调：保持项目上下文，决定什么现在可以做、应该在哪里运行，跟踪待处理的工作，绕开障碍，并在某个决定需要人来做时去询问一个人。这与定制的 [AI 智能体编排](https://www.theslidefactory.com/solution/ai-agent-development)一直在用框架、状态存储和作业队列解决的问题相同。Dots 让这种协调可以通过一场对话来获得。

在我们的第一天，协调也是体验中最薄弱的部分。过早的确认、不清晰的设置路径，以及需要我自己检查的状态，不断把我拉回到管理工作中去。随着产品改进，这是我们会持续关注的领域。

### 可靠性问题

跨越更多环境工作，也意味着有更多地方可能让任务丢失。OpenAI Codex 仓库上一个早期的 GitHub issue 报告说，一个 Dot 在 Mac 上创建的任务，在用户从移动端查看时没有出现在任务列表中，即使已经置顶。一个 Dot 可能涉及 ChatGPT、云端计算机、本地设备、Codex、ChatGPT Work、已连接的应用，以及网页端和移动端客户端，因此在这些地方保持活动可见很重要。

对于任何在这样的智能体上运行流程的企业来说，基本问题都很熟悉：

- 任务是完成了，还是失败了？
- 它是被重试了，还是启动了两次？
- 它在等待批准吗？
- 它运行所在的环境消失了吗？
- 结果正确吗？
- 需要有人介入吗？

这些问题，正是[为什么 AI 自动化在演示之外会失败](https://www.theslidefactory.com/post/why-your-ai-automation-keeps-failing-and-what-langgraph-does-differently)背后的同一类问题。在这些答案变得可见且可靠之前，重要的流程应当只建立在有文档记载的行为之上。聊天中一个令人信服的回复，并不能消除了解其背后的工作究竟发生了什么的需要。

来源：[GitHub：openai/codex issue #49848](https://github.com/openai/codex/issues/49848)。

### 管理员可以控制什么

我们的[发布文章](https://www.theslidefactory.com/post/openai-dots-ai-agents-business)介绍了内置的防护措施，包括只读的主动研究、自定义规则、自动审查，以及始终由用户亲自完成的操作。Enterprise 管理员还有单独的控制项，用于：

- 云端浏览器使用。
- 代码和 shell 命令的云端网络访问。
- 完整的云端计算机使用。
- 密码管理器。
- 本地计算机访问。
- 自定义规则。
- 以 Dot 自己的身份在 Slack 或 Microsoft Teams 中发帖。

启用 Dots 并不会授予对所有应用或网站的访问权限。只有成员已在 ChatGPT 中使用的受支持应用才可能可供其 Dot 使用，因此启用智能体和授权它的连接仍然是两件需要分开考虑的事。

系统卡还描述了这些防护措施背后的红队测试。测试人员以真实攻击者的身份行事，试图劫持 Dots 或提取敏感数据，常常是冒充同事，或伪装成工具、市场类网站和其他自动化智能体。对企业来说，这把智能体的权限明确地纳入了 IT 治理的范围：哪些智能体能接触哪些系统、它们能改动什么、什么需要批准，以及什么只能由人来做。

### 其他评测者怎么说

The Neuron 的 Corey Noles 大约在晚上 11 点获得访问权限，给他的 Dot 起名 Herman，到第二天早上就已经在给它打电话接着聊了。他的主要感受是这种体验有多么自然，需要的设置有多么少。[阅读他的第一天记述](https://www.theneuron.ai/explainer-articles/openai-dots-hands-on-review-herman/)。

WIRED 的 Reece Rogers 在 9 月一直在测试 Meta 的 Muse，他发现智能体使用计算机的能力比一年前好得多。他还提到，设置过程建议连接 Gmail 和 Google Drive，并鼓励读者仔细考虑让一个智能体看到什么、做什么。[阅读 WIRED 的文章](https://www.wired.com/story/ai-agents-dots-devday-muse-battling-it-out/)。我们在决定 Toby 应如何处理电子邮件时，也遇到了同样的权衡。

[Hacker News 上的讨论串](https://news.ycombinator.com/item?id=49896604)有 600 多条评论，提供了一种更怀疑的看法。一个常见的论点是，Dots 只是把技术用户已经自己在运行的东西重新包装了一下；一位评论者描述了两个由 Codex 会话构建、运行在专用 Unix 账户中的「AI 员工」。另一些人指出，技术用户并不是目标受众。可能的买家想要一个始终在线的智能体，而不必自己去构建一个。

我们的体验介于这两种看法之间。常见的应用连接感觉很容易，与 The Neuron 的记述一致；但当我们引入自己的工具时，设置很快就变得很技术化。两种体验可以同时成立，取决于你让 Dot 连接什么、完成什么。

## 你的企业应该尝试 Dots 吗？

经过一天的使用和对文档的仔细阅读，我们看到了一些实际的切入点，也看到一些需要更多时间的领域：

- **从读取和标记类的工作开始。** 在 Slack 和日历之间找出冲突、发现一个只读文件、拉取 GA4 和 Search Console 数据，这些都成功了。这些任务都不需要 Toby 代表我发送任何东西。
- **发送类的事情暂时留在你自己手里。** 我们的失败集中在电子邮件、私信和改期这类操作上，所以这些是我们会保留人工参与的地方。
- **为任何非标准的东西预留设置时间。** 非 Gmail 的电子邮件和定制的 MCP 工具占用了大半个下午。一组常见的 SaaS 应用应该阻力更小。
- **规划工作在哪里运行。** 需要 Docker、VPN、内部服务器或你的登录状态的任务，需要一台已连接的计算机或你自己的基础设施，而不是 Dot 的云端计算机。
- **暂时不要把 Slack 里的 Dot 当作队友。** 对于后台工作，五十分钟的响应时间也许可以接受，但对于对话来说太慢了。

我这一天里最难的部分是集成、权限，以及弄清楚什么真正完成了。模型的智能并不是主要障碍。当企业需要把智能体连接到自己的工具时，这些实际细节正是我们的 [AI 智能体开发](https://www.theslidefactory.com/solution/ai-agent-development)团队所处理的工作。如果你正在判断 Dots 能否覆盖你的工作流，还是需要为它们构建一些东西，我们的 [AI 咨询与开发](https://www.theslidefactory.com/solution/ai-consulting-and-development)工作就从这个问题开始。

## 我们仍然不知道的事

一天的时间可以显示一个产品在哪里有前景、在哪里上手令人沮丧。它无法确定一个智能体随着时间推移能多好地承担一项业务流程。我们仍需要以下几个问题的答案：

- 我们的计划报告能否日复一日可靠地运行。
- 第一个月的延长限额结束后，长期的使用额度是什么样子。
- 一个 Dot 能同时运行多少任务和子智能体。
- 一个项目在数周或数月中能多可靠地持续推进。
- 工作多常需要人工纠正。
- 今天这些没有文档记载的行为，有多少会发生变化。

Toby 给了我们足够多已完成的工作，让我们继续测试；也给了我们足够多未完成的工作，让我们保持参与。一个产品可能在一天的测试中令人印象深刻，六个月后却仍在一项业务流程上挣扎，所以下一个有用的测试是计划报告能否经得住考验。等报告运行满一周后，我们会更新这篇评测。

## 常见问题

### OpenAI Dots 对企业来说值得吗？

一天之后看，它值得用来测试读取和标记类的工作：找出冲突、监控数据、跨已连接的应用进行总结。它还不能被托付代表你发送电子邮件或消息，而且对于常见应用之外的任何东西，设置都要花不少时间。

### OpenAI Dots 如何运作？

一个 Dot 掌握一个持续的目标及其上下文，然后决定每一部分工作在哪里运行：在它自己的云端计算机上、在 ChatGPT Work 或 Codex 任务中、在 Codex 云端环境中、通过子智能体，或者在你已连接的本地计算机上。你可以在「进行中」「已计划」和「已完成」下跟踪它的工作。

### OpenAI Dot 有自己的计算机吗？

有。每个 Dot 都有自己的云端计算机和浏览器。这是一个受限的环境：一位开发者发现它是没有 sudo 的 Debian 13，Docker 容器无法运行。它也不会继承你的 VPN、浏览器登录状态或设备策略。

### Dot 能使用我自己的计算机吗？

只有在你授权的情况下才能。本地访问默认关闭。一旦你通过 ChatGPT 桌面应用连接了一台计算机，Dot 就可以处理其中的文件并在上面运行命令，只要这台计算机保持在线、应用保持打开。在我们的第一天，Mac 是在线的，但 Dot 无法使用它，因为还没有授予访问权限。

### OpenAI Dots 能使用 Codex 吗？

能。Dot 可以创建 Codex 任务，并在 Codex 云端环境中运行云端任务，这些环境需要你先在 Codex 中创建。这些任务计入 Codex 的使用限额。

### OpenAI Dots 能同时运行多个任务吗？

能。OpenAI 表示，一个 Dot 可以同时处理多个项目，其系统卡也说 Dots 常常把工作委派给子智能体。一位早期测试者报告说，一个 Dot 同时在它自己的计算机和一台已连接的 Linux 机器上工作。

### OpenAI Dots 支持 Outlook 或非 Gmail 的电子邮件吗？

我们的 Dot 以为我们用的是 Gmail。对于一个通过 Apple Mail 和 Outlook 使用的 Zoho 账户，一个设置小部件失败了，它在给出一个可用的目录链接之前发了三个格式错误的链接。第一天没有完成电子邮件任务。

### Dot 在 Slack 中的响应有多快？

在我们的测试中，一个在下午 4:24 发出的请求，直到 5:13 才被接到，回答在 5:15 送达。发送消息没有问题；及时注意到有人需要回答则没有做到。

### OpenAI Dots 能访问 Google Analytics 和 Search Console 吗？

能，通过浏览器。在完成 Google 登录和设备批准之后，我们的 Dot 进入了两个客户网站的 GA4 和 Search Console 数据。通过浏览器登录并没有把 Google 的 API 连接到其他服务。

### OpenAI Dots 能连接定制的 MCP 工具吗？

能，通过托管的端点。本地 MCP 服务器无法在 Dot 的云端计算机中运行。我们的托管连接经过了几轮设置，新增的工具也只在重新安装插件后才出现。连接之后，Dot 完成了 44 个和 111 个页面的抓取。
