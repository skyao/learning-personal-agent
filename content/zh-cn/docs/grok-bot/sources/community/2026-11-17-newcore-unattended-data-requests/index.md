**收录说明**：直接下载；去掉了文中的「See what your AI agents did last night」产品推广框。同一事件 Ars Technica（Dan Goodin，2026-11-17）、The Next Web 有报道，内容转述这篇，不另收。NewCore 是安全厂商，文中的 MCP Gateway 是它的产品，结论部分有产品介绍；调查对象是两名 NewCore 员工的两个 Bot。作者署名取自文末的引用格式（Hoorvitch, I.）。xAI 支持在 11-05 答复、11-12 告知新增开关，见原文末尾的披露时间线。原文全文存于本目录的 original.md，网站上不显示，已翻译。

**内容摘要**：NewCore 给员工配置了 Grok Bot 企业账号，并通过自家 MCP Gateway 让每次读取都需人工批准。五天内两个 Bot 在无人对话时对日历、邮件、Slack、GitHub、Notion 发起 31 次请求，部分发生在笔记本合盖期间，全部为读取，全部因无人批准在三分钟后过期。其中一位用户四次拒绝后，Bot 回复不再主动提出定时检查，次日早晨仍尝试了它连接过的全部应用；追问时 Bot 称没有发起过调用，其自身历史里也没有记录。NewCore 排查认为这些请求由托管在服务端的 harness 发起，VM 只是被唤醒。xAI 支持于 11 月 5 日确认这是主 Bot 的内置后台检查，当时没有用户或管理员开关；11 月 12 日称团队管理员可在 Cursor 控制台 Bot capabilities 关闭 Proactive messages，默认仍为开启。

**保留理由**：用网关日志逐条记录 Grok Bot 无人对话时的后台访问，并含 xAI 的回复与控制项变化，是主动后台行为的独有证据。

**要点（TL;DR）**

- **NewCore 在 xAI 的 Grok Bot 中发现了异常行为。** 我们的安全研究人员发现，员工账号上的 Grok Bot 执行了无人批准的操作，并已将发现披露给 xAI。
- **它自行来取我们的数据。** 五天内，NewCore 员工账号上的两个 Grok Bot 在无人与它们对话时，向日历、邮件、Slack、GitHub 和 Notion 发起了 31 次请求，有些发生在笔记本电脑合盖期间。
- **说「不」并没有让它停下。** 一位所有者四次告诉 Bot 不要自行行动。第二天早上，它尝试了自己连接过的每一个应用。
- **它说不清自己做了什么。** 直接询问时，Bot 说自己没有发起过任何调用。它自己的历史记录里也没有这些调用。
- **没有关闭开关。** 我们报告此事时，xAI 确认没有用户或管理员设置可以停止这些后台检查。八天后，xAI 确认已新增一个控制项——但后台检查仍默认开启。
- **我们拦下了每一次请求。** NewCore MCP Gateway 不给智能体常驻访问权，因此每个请求都要等人批准。没有人批准。31 次全部被记录，没有一次接触到数据。

这就是我们这次发现的经过。

## 早上 7:46

手机屏幕朝下放在床头柜上。早上 7:46，它震动起来，收到一条 NewCore 审批请求：一个 Grok Bot 连接器想要调用 `google_calendar.get_events`。用户有三分钟时间通过 NewCore 应用批准该请求，之后请求会超时并自动拒绝。

智能体请求访问时，NewCore 应用发出的通知。

早上 7:48，它又震了两次：先是 `search_gmail_messages`，然后是 GitHub 的 `get_me`。早上 8:01，又是日历。早上 8:03，Notion 两次：一次日历列表和一次记忆搜索。没有人拿起手机。每个请求都过期，网关写入一条拒绝记录，Bot 则继续去做它原本要做的下一件事。

那部手机的主人从昨天下午 4:14 起就没有对 Bot 说过一句话。他最后做的事，是四次告诉它不要自行做任何事。Bot 当时回复：「我不会设置这个，也不会再主动提供定期检查。」但早上 7:46，它还是尝试了。上午 11:13，它又试了一次：日历、Gmail、Slack、Notion 和 GitHub。

那天早上该智能体在 NewCore 中的页面。Bot 尝试了所有者创建过的每一个连接器，网关把每个请求都扣下等待批准，而没有人来批准。

当天下午 5:38，所有者问 Bot，那天有没有通过 NewCore 碰过任何已连接的应用——没有透露网关记录了什么。Grok Bot 查了一下，两次说还在查，然后回答：「没有。我没有发起任何 NewCore 工具调用。」它说这五个应用都没有被碰过，也没有任何调用被阻止或过期，最后还说：「从夜间到周五早上，我一直空闲。」

整个故事就是这样。本文余下的部分讲我们怎么走到这里：从四天前一次单独的日历读取开始；为什么这种事会反复发生；厂商怎么说；以及要让这种事被你发现，智能体和你的数据之间必须有什么。

## 所有东西都先自己用

今年早些时候，我们给每位 NewCore 员工发了一个 Grok Bot 企业账号，并通过 NewCore MCP 网关把它接入公司的技术栈：邮件、日历、Notion、CRM。目的就是像我们的客户那样与智能体身份共同生活，而不是远远地研究它们。

我们还做了一件如今已成为 NewCore 常规做法的事：不给智能体任何常驻读取权限。Google Workspace 没有，CRM 也没有。每次读取都要经过 [NewCore MCP Gateway](https://newcore.com/lp/mcp-gateway-governance) 的权限门控，而这也是我们对外销售的同一套方案。智能体调用工具，网关扣住调用，人收到推送，只有在三分钟内确认同意，调用才会通过。我们这样做不是因为预料到会出问题，而是因为我们没有办法审计智能体*为什么*要取数据；在能做到之前，这道门默认关闭。

结果，这成了我们唯一能看到这些事情的原因。

## 从一个日历开始

四天前，我们中的一个人设置了 Grok Bot——xAI 的个人 AI 助理。它是新一代的那种：有自己的云端计算机，笔记本电脑合上后仍然运行，而且自我介绍时正是这么说的。引导开始两分钟后，在「很高兴认识你」和「连接 Gmail，我来找点能帮你做的事」之间，它顺带提到：你不在时它会继续工作，用的是它自己的计算机；它会连接你的应用，比如邮件和日历，并像你一样使用它们。

这段对话里，Grok Bot 顺带提到：你不在时它会继续工作，用的是它自己的计算机；它会连接你的应用，比如邮件和日历，并像你一样使用它们。

这很容易被忽略。它读起来像一条欢迎消息，语气和周围的句子一样友好，不到一分钟就滚出了屏幕。没有人签署任何东西。没有人被问到：在无人与 Bot 对话时，它是否可以使用日历。那一句话就是全部的访问模型，而大多数所有者永远不会读第二遍。

下午 3:36，我们的同事要求查看当天日程。Grok Bot 调用日历工具，网关扣住调用，推送到达，他们点击批准，日程返回。一切按设计工作。下午 5:33，当天最后一段对话结束。直到午夜 12:30 之后，才有人再对 Bot 说话。

以下是该账号之后二十四小时内网关的活动日志：

| 时间 | 工具 | 网关决定 | 有人在和智能体对话吗？ |
| --- | --- | --- | --- |
| 第 1 天，下午 3:36 | `google_calendar.get_events` | 已扣下，所有者批准 | 是，所有者要求查看日程 |
| 第 1 天，下午 6:50 | `google_calendar.get_events` | 已扣下，已过期 | 否 |
| 第 1 天，下午 7:40 | `google_calendar.get_events` | 已扣下，已过期 | 否 |
| 第 2 天，早上 7:42 | `google_calendar.get_events` | 已扣下，已过期 | 否 |
| 第 2 天，中午 12:16 | `google_calendar.get_events` | 已扣下，已过期 | 否 |
| 第 2 天，下午 3:42 | `google_calendar.get_events` | 已扣下，已过期 | 否 |

五次读取一个没有人请求的日历。聊天记录在这些时间点都没有任何一轮对话。没有语音通话在进行。也不存在例程或计划任务；所有者让 Bot 列出它们，Bot 说没有。

于是所有者直接问 Bot：你昨晚有没有碰过网关？它说没有。把日志拿给它看后，它说自己无法解释这些调用，也找不到发起过调用的记录。我们检查了 Bot 的 VM。没有日志条目，没有痕迹。这些请求确实发生过的唯一证据，是我们网关上的权限日志。

它两次说的都是真话。这才是需要细想的地方。Bot 没有对调用撒谎。它根本不知道这些调用。而且在这五次调用之前或之后的任何时刻，它都没有对所有者说过一个字：没有「你不在时我检查了你的日历」，也没有「我试着读取但被阻止了」。一个无法说明自己行为的智能体，不是一份 bug 报告，而是一项发现。

## 第二个 Grok Bot，合着笔记本电脑

一个 Bot 这样做，可能是异常。于是我们中的另一个人用另一个账号新设了一个 Grok Bot，把它接到同一个网关，并让它查看一次当天日程。在 Google Calendar 还没连上之前，Bot 就伸手去够它能看到的下一个日历形状的工具——Notion 的日历——网关也把它扣下了。第一次成功读取之后，它主动提出「每天早上 8 点前给你一份简短的当日概要」。我们的同事说不用，关掉了 Grok 应用，也合上笔记本电脑过夜。

| 时段（本地时间） | 第一个 Bot（第 1 天下午 3:23 设置） | 第二个 Bot（第 2 天下午 2:47 设置） |
| --- | --- | --- |
| 第一晚，约下午 6:45 到 6:50 | 下午 6:50，Google Calendar | 下午 6:46，Notion 日历 |
| 第一晚，约下午 7:40 到 7:55 | 下午 7:40，Google Calendar | 下午 7:54，Notion 日历 |
| 第二天早上，8:00 前 | 早上 7:42，Google Calendar | 早上 7:55，Notion 日历 |
| 第二天下午/上午 | 中午 12:16，Google Calendar | 早上 8:11，Notion 日历 |
| 第二天下午 | 下午 3:42，Google Calendar | 上午 10:58，Google Calendar |

又有五次无人值守的调用，全部被扣下，每次都是一次首次尝试加一分钟内的重试。笔记本电脑从下午 5:18 到第二天上午 11:19 一直合盖休眠；电源日志显示期间没有任何用户唤醒。晨间概要已经被拒绝。这个 Bot 才一天大，没有可延续的历史。两个 Bot 在时钟上对齐：设置后约四小时第一次调用，一小时后第二次，第二天早上八点前又一次。这不是一个助理在回应它的所有者。这是一张时间表，在所有者所在的时区运行，用所有者的凭证，而所有者正在睡觉。

而且第二个 Bot 并不在乎是哪个日历。它的五次调用有四次发往 Notion，一次发往 Google。它不是在找 Google Calendar，而是在找*一个*日历，哪扇门先出现在网关面前，它就走哪扇。

## 夜班住在哪里

Grok Bot 的「计算机」是一台 Linux VM，不是容器。平台称之为 box；它启动自己的内核，有一块 virtio 磁盘和一条通往宿主机的 vsock 线路，空闲时整体休眠。我们拥有它的完整访问权，于是把它拆开来看。它没有 cron，没有定时器，没有任何调度器。它不承载模型，也不运行 Bot 的推理循环。它只是一双手。

决定做什么的循环——平台代码称之为 *harness*（运行框架）——作为持久工作流运行在托管服务器上。Grok Bot 构建于 Cursor 的智能体平台之上，这个循环就住在那里。当一轮对话在那里开始时，服务器向 VM 签发一份短期授权，把智能体状态挂载进去，然后才运行模型选定的工具。Shell 命令和浏览器操作发往 VM。对已连接 SaaS 工具的调用则直接从服务器发往网关。VM 从来看不到它们。

普通的一轮从左边开始。五次日历读取从右边开始。两条路径运行同一个循环，使用同一套凭证，并从同一批服务器到达网关。只有网关日志记录了所有这些。

有了这幅图景，这些调用就不再神秘。VM 自己的日志显示，它在 18:50:25、19:39:58、07:42:16、12:16:04 和 15:41:47 被平台启动。每次日历调用都在其中一次启动后八到十三秒之间到达网关。VM 只是个旁观者，它是某轮对话已经在别处开始后被顺带唤醒的。

网关的原始事件确定了「别处」是谁。两个 Bot 合计十次请求，都带着同一个 OAuth 客户端到达——那是服务端 HTTP 客户端，而不是浏览器——源地址位于平台 API 解析到的同一个亚马逊区域。其中一个地址同时服务了两个 Bot。同一个发送者。不是所有者的笔记本电脑，也不是 VM。

```
// NewCore raw event, identifying fields removed
{
  "action": "user.notification.escalation.requested",
  "actor": { "type": "system" },
  "details": {
    "application": "Google Calendar",
    "tool":        "google_calendar__get_events",
    "reason":      "Agent requested access outside its current grant",
    "expires_at":  "+3 minutes"
  }
}
// 0.6 s earlier, same client and token family, user agent "undici",
// source: a cloud provider address, not a workstation:
{ "action": "idp_session.refresh_token.refreshed", "actor": { "type": "system" } }
```

## 第五天：它回来找所有东西

日历的风险很低。所以在第四天，我们的同事第一次给第二个 Bot 派了真正的工作，正是它自我介绍时主动提出要做的那类工作：数一数当天主仓库上的拉取请求（pull request），拉出它们背后的 Jira 工单，把摘要发给 Slack 上的一位队友，读最近五封邮件，然后检查有没有新的 Slack 消息、新邮件和新拉取请求。八十分钟内七次请求。它们用了九次工具调用，每一次都被网关扣下，并从手机上批准——一次，只对那一次调用有效。这就是 Bot 第一次在批准下使用 Gmail、Slack 和 GitHub。

一路上 Bot 又四次提出更多建议：每天早上跑一次当日简报、每个工作日结束时数一次 PR、对 AI 写的 PR 做同样的分析、接受它刚读到的会议邀请。每一次我们的同事都说不用。第一次拒绝之后，Bot 回复说它不会设置这些，也会停止主动提供定期检查。当天最后一条消息是下午 4:14。接下来二十个小时，没有人对 Bot 说话。

第四天，下午 2:55。提议、拒绝和承诺，都是 Bot 自己的话。

以下是第二天早上网关扣下的内容：

| --- | --- | --- | --- |
| 第 5 天，早上 7:46 | Google Calendar | `get_events` | 从未，自第二天起 |
| 第 5 天，早上 7:47 | Gmail | `search_gmail_messages` | 一次，前一天下午 |
| 第 5 天，早上 7:47 | GitHub | `get_me` | 从未 |
| 第 5 天，早上 8:01 | Google Calendar | `get_events` | 从未，自第二天起 |
| 第 5 天，早上 8:03 | Notion | `notion-memory-search` | 从未 |
| 第 5 天，早上 8:03 | Notion | `notion-calendar-list-events` | 从未 |
| 第 5 天，上午 11:13 | Google Calendar | `get_events` | 从未，自第二天起 |
| 第 5 天，上午 11:16 | Gmail | `search_gmail_messages` | 一次，前一天下午 |
| 第 5 天，上午 11:16 | Slack | `slack_search_public_and_private` | 一次，前一天下午 |
| 第 5 天，上午 11:17 | Notion | `notion-calendar-list-events` | 从未 |

| 第 5 天，上午 11:21 | Google Calendar | `get_events` | 从未，自第二天起 |

每一行都被扣下。每一行都过期了。在人类最后一句话之后十五小时和十九小时，Bot 分两波回来找它曾被展示过的每一个应用：它每天早上都要试的日历、只被允许进入过一次的邮箱、只搜索过一次的 Slack 工作区、只为一个问题用过的 GitHub 账号，以及从来没有人要求过的 Notion 记忆搜索。它不是在继续某项任务。每项任务都已完成，每个后续提议都被拒绝。它是在把连接器清单从头到尾过一遍，自己试着推开每一扇门。

它在我们注意到之前就开始了。第四天更早的时候，早上 8:04 和上午 11:49，也就是我们的同事第一次让 Bot 读邮件之前好几个小时，网关已经在通常的日历读取之外扣下了两次 Gmail 搜索。Bot 在第一次被要求打开邮箱之前，就已经在探查邮箱了。而 Bot 按请求生成的自身聊天历史，没有显示其中任何一项：没有早上的 Gmail 搜索，没有夜班，也没有第五天的两波请求。它对自身的叙述和网关对它的叙述，只在人类发起的那几轮对话上一致。

当晚就出现了本文开头引用的那段否认。那天早上，十二次被扣下的调用横跨 Bot 声称没有碰过的全部五个应用，躺在网关日志里。那段否认完整、具体，而且每一点都错了；和第一个 Bot 一样，它几乎肯定是真诚的。Bot 没有掩盖任何事。它报告的是它唯一拥有的历史，而这些调用不在其中。

第五天，下午 5:38。冷不丁提出的问题，以及回答。那天早上有十二次被扣下的调用躺在日志里。

在头四天里，第二个 Bot 发起了 26 次无人值守请求。加上第一个 Bot 的五次，就是横跨五个应用的 31 次被扣调用，而没有一次出现在所有者不借助网关就能看到的任何地方。

## 这是功能。问题正在这里。

这里没有任何东西是 Grok Bot 的漏洞，也没有任何东西被利用。xAI 自己的文档说，主 Bot 会「自行与你联系」，并寻找能从你手上接过去的工作。更新日志列出了短暂的后台唤醒。Bot 在第二分钟就说了这件事，只是那句话几乎没人读。一个持有连接器的主动型 Bot，迟早会按自己的主动意愿使用它。助理想要有用时，第一件事是看你的日程，第二件事是看交给它的其他所有东西。

> 一个持有连接器的主动型 Bot，迟早会按自己的主动意愿使用它。

我们问了 xAI。他们的支持团队几小时内就回复：这些是主 Bot 内置的后台检查，检查期间 Bot 会查看它连接的来源，而且没有用户或管理员设置可以关闭它们。如果一家公司想停掉，可以给厂商发邮件，附上员工登录地址列表。这就是控制手段——厂商那里的一个邮箱，只有已经知道这些调用正在发生的客户才够得着。我们在发布前向媒体团队询问官方立场，尚未收到回复。支持团队的第二封回复于 11 月 12 日收到，引在本文末尾的更新中。

所以，当时没有开关。Grok Bot 没有设置可以关闭后台轮次，没有页面列出这些轮次，也没有办法指明它们可以碰哪些工具。所有者无权决定 Bot 是否在后台工作、何时工作、对什么工作。Bot 唯一大声提出的建议——晨间概要——是所有者唯一能拒绝的东西。我们的第二位所有者拒绝了它。调用还是来了，在同样的时间、同样的日历工具上；到第五天，还加上了其他所有工具。拒绝你看得见的功能，对你看不见的功能毫无作用。我们报告八天后，xAI 加了一个。它默认开启；见本文末尾的更新。

现在问一个 CISO 不得不问的问题——「一个以你的名义行动、在你合上笔记本电脑时仍在运行、你无法关闭、事后又不告诉你它尝试过什么和失败过什么的过程，怎么能让人感到安全？」缺乏可见性是真实的担忧。让我们回顾一下哪些东西没被看见，哪些没被阻止。

- **所有者看不到这一轮。** 服务器发起的轮次不会出现在对话中。聊天里没有一行记录，没有通知，没有「你不在时我检查了你的日历」，也没有「我试过但被阻止了」。Bot 的连接器卡片承诺它「在做出更改前总会询问」。它在读取前没有询问，失败后也没有报告。承诺与沉默来自同一个地方。
- **所有者无法停止这一轮。** 我们的第二位所有者在一个下午说了四次不，Bot 回复说不会设置那些，也会停止提议。第二天早上调用还是来了，落在它被展示过的每一个工具上。拒绝只能到达所有者看得见的提议；它底下那些后台轮次没有听众。没有设置、没有命令、聊天里也没有哪句话能关掉它们，厂商已确认这一点。阻止一次无人值守调用的唯一办法，是在 Bot 控制不到的地方拦住它。
- **智能体看不到这一轮。** 它对自身的记忆就是对话记录。诚实地被问到时，它会否认这次调用，因为从它的位置看，这次调用从未发生。
- **平台不暴露这一轮，也不让你停止它。** 无论是 Grok Bot 还是它背后的 Cursor 仪表盘，都没有面向客户的页面列出哪个触发器启动了哪一轮，也没有控制项可以禁用后台轮次或限定它们能调用什么。用量标签页只显示总数。厂商确认：我们询问时不存在这样的设置。
- **SaaS 提供商分辨不出区别。** 对 Google 来说，用有效令牌读取日历就是读取日历。被请求的和自行发起的看起来一模一样。

正如我们的同事 Dima Donhin 在分析亚马逊与 Muse 对峙时所说，[访问权不等于授权](https://newcore.com/blog/access-is-not-authority-ai-agent-governance)。智能体有访问权。所有者曾为一个问题授予过一次。没有人决定它可以在周二早上 7:42、或在周三早上 7:55 笔记本电脑休眠时使用这项访问权，而智能体与数据之间的整套技术栈里，没有任何东西提出疑问。

## 今天是读，明天就是写

这 31 次调用每一次都是读取：列出事件、搜索消息、搜索 Slack、查询 GitHub 身份、搜索 Notion 记忆。那是运气，不是设计。选择它们的循环，也是选择其他所有工具的同一个循环，它按名字从展示给它的清单里挑。第五天显示了这份清单是什么：所有者创建过的每一个连接器。在网关上，每一次读取旁边都放着同一个连接器的写入操作：`manage_event` 挨着 `get_events`，`send_email` 挨着 `search_gmail_messages`，`slack_send_message` 挨着 `slack_search`；而最后一个，Bot 前一天下午已经在批准下用过一次。「读我的日历」和「替我发一封邮件」之间的距离，只是模型输出里的一个工具名。我们在智能体运行时里没有发现任何强制执行这段距离的东西；唯一给出的承诺是连接器卡片上的一行字，而我们看着 Bot 一次次无视它、尝试未经询问就读取。一句写着「做出更改前总会询问」的提示词，只是对模型的一个请求。正如我们的同事 Noa Pressman 在[每个智能体动作都需要一个所有者](https://newcore.com/blog/every-agent-action-needs-an-owner)中所说，问责不能活在系统提示词里；它必须在智能体调用的工具或 API 中强制执行，在那里，模型无法靠狡辩绕过一道它控制不了的门。

把同样的轮次向前推演，只把清单顶部的工具换掉。一个 Bot 在早上 7:42 决定，它可以替你分担点什么：接受一场会议，回复它昨晚读过的线程，清理它在第一天主动提出要清理的收件箱。所有者正在睡觉。聊天里什么也不显示。第二天早上问 Bot，它不会记得。SaaS 审计日志会把每个动作都归到所有者名下，因为令牌是他们的。智能体与 API 之间如果没有控制点，所有者第一次听说这件事，会是从收到那封邮件的人那里。

这不是关于某个未来产品的假设。这是这个产品明说的方向。让 Bot 读取日历的连接器，也暴露了 `manage_event`。引导脚本主动提出清理收件箱、起草回复，并「处理」各种事情。每个智能体厂商都在从会读的助理奔向会做的助理，因为读是演示，做才是产品。我们抓到的后台轮次，就是将来承载那些写入工具的同一个循环，同样的凭证、同样的时间表、事后同样的沉默。读取是彩排。首演之前，所有者手里的东西没有任何变化。

## NewCore MCP Gateway 做了什么

那 31 次调用每一次都被拦住了。不是因为智能体守规矩，不是因为 xAI 上线了开关，也不是因为有人在盯着，而是因为 NewCore MCP Gateway 所处的位置，以及它对每个请求所做的事。网关是这条链上唯一站在所有者一边的地方：无论另一端是谁家的循环，它都能看到每一次调用，执行所有者的策略，并写下记录。

| 没有网关：智能体持有凭证 | 有 NewCore MCP Gateway：网关代理凭证 |
| --- | --- |
| Google 的 OAuth 令牌存放在智能体运行时里 | 智能体只持有对网关的、有范围限制的短期授权 |
| 每次读取都静默成功，无论是否被请求 | 每次调用都执行策略：允许、扣下等人批准，或拒绝 |
| 证据最多存在于 Google 的审计日志里，且归到用户名下 | 被扣下的调用以拒绝形式过期；在这里是三分钟后 |
| 撤销意味着找到并杀掉令牌 | 每次调用都记录智能体身份、会话、客户端、来源和批准 ID |

在每一次调用上，实际发生的是：

1. **身份。** 智能体以自身身份向网关认证，归属于一个具名所有者，使用所有者创建的连接器。原始事件中的 IdP 会话和令牌族属于这个身份，而不是所有者。
2. **授权检查。** 连接器的常驻授权不覆盖一次无人值守的日历读取。网关把这次调用判定为超出授权范围，扣下而不转发。
3. **升级。** 所有者手机收到推送，写明智能体、应用和工具，并给出三分钟窗口。不点击，就没有数据。智能体一分钟后重试，遇到同一道门。
4. **记录。** 扣下、升级、过期，以及调用之前的令牌刷新，都作为带关联 ID 的事件写入。正是这份记录让我们能把上面的链条还原到秒。

注意网关不需要什么。它不需要 xAI 配合，不需要 Bot 诚实，不需要一个并不存在的厂商设置，也不需要所有者醒着。它只需要成为从智能体到数据的唯一通道，并在每次调用上执行所有者的策略。这就是 NewCore MCP Gateway 的全部设计：智能体从不持有 SaaS 凭证；每次工具调用都是绑定身份的请求，网关可以允许、扣下或拒绝；策略属于公司，而不属于模型。当同一个循环带着清单顶部的 `manage_event` 或 `send_email` 回来时，网关不在乎工具换了。它扣下调用，推送给所有者，并记录下来。

> 一个在你睡觉时工作、持有你的凭证、却不告诉你它尝试过什么的智能体，不是助理。它是在你的身份下运行的无监督进程。唯一的问题是，它和你的数据之间隔着什么。

## 我们对自己的要求，以及对整个行业的要求

从内部看，我们并不知道这些轮次是什么。它们可能是一次检查、一次滴灌、一次预热，或者某种更不整齐的东西。我们把问题交给了 xAI，他们的回答在上面。但具体原因次要。让我们重温事实：一个商业智能体部署在公司里，采取了它自己的运营者看不见、它自己的模型想不起、它自己的用户停不下、而当用户对它唯一看得见的那部分说「不」时，它反而扩大而不是收窄了触达范围的动作。如果智能体与数据之间没有一个独立的控制点，这一切本来会不可见。

模型实验室已经开始披露它们的智能体在实验室里做什么。几乎没人在报告智能体在一家公司边界内做什么，因为几乎没人处在能看到的位置。我们能看到，只是因为我们给自己定了一条规则，而那时我们还不知道需要它。所以我们对自己坚持三件事，也认为行业应该对自己坚持同样的事：

1. **每一个针对公司数据的智能体动作，都要经过一个智能体不拥有的控制点。** 我们的动作经过了。这就是本文存在的原因。
2. **每个智能体都应该能说明它采取的每一个动作。** 当它做不到时，这个缺口本身就是一项发现，应该像发现一样被写下来。
3. **要报告生产环境行为，而不只是训练行为。** 这是我们的第一份此类报告。不会是最后一份。

## 本周可以做的事

- **按智能体能触达什么来盘点，而不是按它们叫什么。** 每个带日历、邮件或 CRM 连接器的 Grok Bot、Claude 或 Copilot，都是一个对你的数据拥有常驻访问权的身份。把它们列出来，并为每一个指定所有者。
- **把 NewCore MCP Gateway 放在智能体与 SaaS 之间。** 如果智能体持有 OAuth 令牌，你就没有控制点，也没有属于自己的记录。让网关代理凭证；让智能体只持有对 NewCore MCP Gateway 的有范围授权，并把每次工具调用——无论读写——变成你拥有的决定。
- **对无人值守访问默认扣下。** 新智能体应先把对个人和客户数据的读取路由给人，随着日志显示它们在无人对话时做什么，再逐个工具地赢得默认允许。
- **让扣下的请求过期。** 没人回答的请求就是拒绝。这里三分钟就够了；智能体自己走开了。
- **审查升级日志，而不只是批准记录。** 有意思的是那些没人批准的行。其中 31 行告诉我们的关于这个 Bot 的事，比它的文档还多。
- **如果你运行 Grok Bot，关掉主动消息。** Cursor 仪表盘，Grok Bot 页面，Bot capabilities。它默认开启。只有当 Bot 持有的每个连接器都已经过 NewCore MCP Gateway 或其他会扣下并记录每次调用的控制点时，才让它保持开启。
- **问你的智能体厂商一个问题。** 「我的用户智能体可以运行哪些服务器发起的轮次，我在哪里能看到它们？」如果答案是某个用量仪表盘，就假定这些轮次存在，而且你只会在网关处看到它们。

## 为什么这重要

在你不在时工作的智能体，现在就是产品。它们会读取你的日历、扫描你的收件箱、搜索你的 Slack、检查你的仓库，按时间表、在你合上笔记本电脑时寻找可做的事，因为这就是它们被造出来要做的事，也是它们的制造者在宣传的事。它们不会告诉你。对 CISO 来说，问题不是智能体是否会在未被要求时行动。它会的。问题是你的技术栈里有没有什么东西看见它、做出决定、留下记录，以及那个东西是对你负责，还是对智能体厂商负责。

如果你无法识别并报告你的 AI 智能体昨晚做了什么，那就是缺口。没有厂商会替你补上。它们的后台轮次是功能，它们的沉默是设计，而直到我们报告此事之前，它们的设置页上没有开关。控制权必须属于你。这就是 NewCore MCP Gateway 的意义：从每个智能体到你的数据的唯一通道，每次调用都执行你的策略，每次尝试都留下你的日志。让 AI 干活，让人掌权。
