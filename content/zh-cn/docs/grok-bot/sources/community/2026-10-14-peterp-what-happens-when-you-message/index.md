前沿实验室里的「Token maxis」一直说，在 AI 时代，系统/分布式工程比以往任何时候都更重要。直到我看了 [Lee Robinson 关于 Grok Bot 如何工作的演讲](https://www.youtube.com/watch?v=L1OBRtfPS34)，才真正明白为什么。

事实证明，现代聊天智能体并不是某种新的软件范式。它由我们一直用来构建可扩展系统的相同部件构成：队列、后台工作进程、持久化工作流（durable workflow）、幂等性、缓存和最终一致性。模型才是新的部分。

让智能体对真实用户有用的每一件事，都是分布式系统的工作。这包括在工作时保持响应、在崩溃后存活，以及连续运行数小时而不烧钱。

本文概述从你按下发送，到智能体重新进入休眠之间发生了什么（并尝试沿途指出那些熟悉的模式）。

其中大部分直接来自 Lee 的演讲，我强烈推荐观看。演讲没有详细展开的地方，我根据自己的分布式系统经验做了补充。

顺便说一句：我创建了一个 Grok Bot，它解析了整个视频（包括截图），并以文本形式整理出来，供不喜欢看视频的人使用。

## 按下发送

当你按下发送时，应用会立即显示你的消息。它不会等待服务器。应用会在本地用唯一 ID 保存这条消息。这个 ID 在服务器端很重要，服务器会丢弃它已经见过的任何消息。网络不稳定导致重试发送时，不会让你把同一条消息发送两次。

这条消息随后加入你对话的队列。

## 队列、批处理与打断

每个对话都有一个队列，任何想要引起智能体注意的东西都会进入其中。不过，并非每条消息都受到同样的对待。

你直接发给 Grok Bot 的消息会打断智能体。如果它正进行到某个回合（turn）中途，而你发送了新内容，它会停下来接收你的消息。其他一切都按顺序等待。这包括已完成的辅助智能体（helper agent）回报、Slack 提及，或计划工作流触发。

这些消息加入队列时不打断。你享有优先权，因为你是那个正在主线程上等待的人（字面意义上）。

如果你非常快地发送三条消息，它们可能不会变成三个独立的回合。大概存在某种很短的节流窗口，把相邻到达的消息归并为一个回合。

## 被打断不等于丢失

主智能体循环是运行在服务器上、使用 Temporal 的持久化工作流。每次模型调用和工具调用都是一步（step），每一步的结果在完成时立即保存。对话历史单独存放在自己的数据库中。

**Temporal 是什么？** 一个开源引擎，会在你的代码运行时保存每一步的结果。如果服务器崩溃，另一台服务器会从上次中断处继续，而不重做已完成的工作。它还处理重试，并让工作流休眠，直到有东西将其唤醒。

「可打断」和「持久化」容易混淆，但它们是两个独立的属性：

- **可打断（Interruptible）** 意味着你的新消息会切断进行中的回合。
- **持久化（Durable）** 意味着到目前为止完成的工作不会被丢弃。下一个回合从已保存的步骤继续。

因此，你可以给智能体发送一百条消息，它会不断被打断，但绝不会重做已经完成的工作。同样的属性使它免受崩溃影响。如果服务器宕机或出错，工作流会从最后保存的步骤恢复，而不是从头开始。

## 服务器实际如何运行这个循环

Lee 提到 Grok Bot 使用 Temporal，但没有深入说明循环如何在它上面运行，所以以下是我最好的猜测。

服务器是始终在线的 worker 进程，由每个用户共享。回合之间，没有任何属于你的东西在运行。

循环是写一次就固定的普通代码，类似 `agentTurn(conversationId)`。当你发送消息时，前门（front door）会保存它并向 Temporal 发出信号。Temporal 创建一个任务，任何空闲的 worker 都会领取它。该 worker 从数据库加载你的对话历史并运行一个回合。从这个意义上说，它的工作方式很像无状态 API 请求（你熟悉且喜爱的那种）：

```
workflow agentTurn(conversation):  messages = loadContext(conversation)   // saved step  loop:    reply = callModel(messages)          // saved step    if no tool calls: break    for toolCall in reply:      result = runTool(toolCall)         // saved step      messages.append(result)  saveTurn()  waitForSignal()                        // sleep
```

Temporal 同时充当调度器和记录者。它一次把每一步交给一个 worker，并记录结果。如果某个 worker 在步骤中途崩溃，它对该步骤的占用会超时，另一个 worker 会从已保存的步骤重放工作流。这就是为什么每次模型和工具调用都会写入数据库：正是这些写入让重放成为可能。

回合结束时，工作流停在「等待信号」。内存中不保留任何东西，也没有任何东西在运行。工作流只是数据库中的一些行。据说智能体会在空闲约两分钟后休眠。我猜那是 worker 在保持热状态，以防你很快回复。

这就是智能体如何做到「始终在线」而实际上并非一直运行。休眠成本很低，因为没有任何状态存在于 worker 本身。

## 快速工作与辅助工作流

现在你的消息已经到达智能体。它会怎么处理？

首先，前门的路由器对触发进行去重，并把它们放入对话的队列。之后，主智能体根据其提示词中的一条经验规则自行决定如何处理请求。它会先向你确认，然后要么自己完成工作，要么把它交出去。

小任务留在主循环中。编辑 Notion 页面或更新 GitHub 评论被认为是快速工作，把它放到后台运行可能比节省的代价花费更多 token 和时间。主智能体也可以运行 shell 命令。不过如果我没记错（IIRC），shell 运行在虚拟机上，所以即使是快速命令也会唤醒虚拟机。任何大量使用 shell 的工作都被视为运行时间较长的工作，会被发送给辅助工作流。

就地完成快速工作的缺点是，你的打断会直接落在它上面。如果你在它编辑那条评论时不断发送消息，编辑就会花更长时间，因为循环不断被切断。我相信 Meta 的 Muse 也是这样工作的。

对于更长的工作，智能体会启动四种辅助类型之一：通用、计算机使用（computer use）、视频和云端编码。每个辅助工作流都是自己的持久化工作流，拥有自己的运行框架（harness）和工具，并且全部在后台运行。当辅助工作流完成时，它会把结果发布到队列，这就是前面提到的非打断消息。

## 虚拟机（VM）

智能体循环运行在共享服务器上。虚拟机是独立的。它是你的智能体自己的计算机，循环有一个工具，在需要时启动它。

服务器是事实来源。你的对话、例程（routine）和工作流步骤存放在数据库中，我猜是像 Postgres 或 SQLite 这样的数据库。你的文件、记忆和技能备份到对象存储，比如 S3 或 R2。虚拟机保存它处理的文件的副本，以及它自己的工作文件：下载的 YouTube 视频、SEC 申报文件、克隆的仓库等。这些文件会一直保留，直到有东西删除它们，而且它们也会同步到对象存储。

当虚拟机休眠时，其内存和磁盘会被制作快照（snapshot）。这意味着你已登录的会话和其他状态得以保留。这也意味着虚拟机是一次性的。如果 Grok Bot 团队需要为零日漏洞（zero-day）修补虚拟机，什么都不会丢失，因为服务器掌握事实来源，而且你的文件都已备份。

这些是 Firecracker 微虚拟机（microVM），如果我没记错，AWS Lambda 和 Fly.io 用的也是同一种。Firecracker 虚拟机非常小，启动大约只需 125ms，从快照恢复也很快。这意味着唤醒虚拟机感觉是瞬时的。

技能（skill）的工作方式相同。内置技能和插件技能来自 Grok Bot 平台本身。你的自定义技能是存放在虚拟机上的 markdown 文件，就像你把它们存在笔记本电脑上一样，并且会备份到对象存储。你的记忆也以同样的方式工作，智能体使用 grep 来搜索它。

## 多个 Bot，一台计算机

你可以创建任意多个 Grok Bot，但它们不会各自获得一台虚拟机。你的所有 Bot 共用一台计算机。它们共享相同的文件、相同的已安装工具和相同的浏览器登录状态，因此如果一个 Bot 安装了某个东西或登录了某个网站，其他每个 Bot 都可以使用它。

每个 Bot 获得的是自己的桌面：在共享计算机上有自己的屏幕和自己的浏览器窗口。一个 Bot 看不到也无法操作另一个 Bot 的屏幕，因此两个 Bot 可以同时各自使用浏览器，而不必争抢鼠标。

这很像几个人共用一台笔记本电脑，每个人都有各自的用户会话，但硬盘是共享的。每个 Bot 在服务器上保留自己的对话、记忆和例程，因此共享计算机只是工作区。

## 保障安全

与 ChatGPT 或 Claude 的自动审查步骤类似，Grok Bot 有一个独立的模型，在智能体的操作运行之前进行审查，主要是 shell 命令。它审查的是智能体即将做什么，而不是你的提示词。

来自外部来源的内容，例如电子邮件和网页，始终被当作数据，而绝不是指令。任何无法撤销的操作，例如发送电子邮件或发布到 Slack，都会以草稿形式回到你这里，先由你批准（想必是在那位老兄的银行账户信息泄露之后）。

## 一个与你对话的工具

无论工作如何完成，结果都以相同方式到达你这里。有一个名为 `SendToUser` 的全局工具，Grok Bot 用它来联系你。无论你是在桌面端、移动端还是 Slack 上，智能体都调用 `SendToUser`，各客户端自行决定如何展示给你。

## 上下文与压缩（compaction）

一个始终可用且记得所有事情的智能体很容易变得缓慢、无用且昂贵。Grok Bot 有四种不同的方法来应对这一点。

### 稳定的提示词前缀

模型提供商会从第一个 token 开始缓存提示词。如果提示词的开头（例如系统提示词加工具列表）在每个回合都完全相同，就可以低成本地复用。任何变化的内容（例如新消息）都放在末尾。

这比听起来更重要。每个回合都会重新发送整个对话（convo），而缓存命中正是让这件事又快又便宜的原因。如果靠近开头的内容发生变化，它之后的所有内容都会错过缓存，成本和延迟都会跃升。这就是团队认真对待缓存未命中的原因。

我是吃了苦头才学到这一点的。你可能记得[我的 X 帖子](https://x.com/peterpme/status/2107847615463219252?s=20)，我在其中估计 poteto 每月在 AI 上花费 1100 万美元。我错了，因为我忘了提示词缓存。把这一点算进去后，真实数字更接近每月 100 万美元。缓存的前缀会带来很大差别。

顺便说一下（btw），大多数模型提供商也是这么做的，不只是 Grok。Codex 和 Claude 也有缓存。

### 延迟加载的工具和技能

就你的技能而言，提示词中只放名称和简短描述。完整的技能只有在智能体真正需要时才加载。这就是 Agent Skills 标准的工作方式，据我所知，Claude、Codex 和 Pi 都遵循它。这就是为什么技能描述应当说明*何时*使用它，而不是里面有什么。模型在决定是否加载技能时，唯一能看到的就是描述。技能不应自动加载。

如果你曾经翻看过 pstack，你会看到一个名为 `disableModelInvocation` 的布尔值。它会阻止模型自行加载技能，因此你必须显式运行它，例如 `/hello-world`。否则模型根本不知道它的存在。

### 较小的主上下文

繁重的工作交给辅助工作流，因此主线程的上下文保持得非常小。让子智能体/辅助工作流按各自的具体工作需要拉取所需内容。

### 上下文压缩

压缩有两种触发方式。第一种在你离开时运行。如果上下文超过 100K token，而你离开了大约 10 到 60 分钟之间的某个时长，智能体就会在后台进行压缩。这个时机很重要，因为压缩需要把整个对话重新送入模型，而在缓存仍然热的时候做这件事可以保持低成本。

第二种触发是达到你的上下文上限。如果你在同一个会话中待得足够久，上下文最终会接近窗口大小，对于 Grok Bot 大约是 200K token（Codex 和 Claude 大约是 1M，但可配置）。

到那时，智能体必须立即压缩并阻塞主线程，因为它无法推迟。我想这种情况发生的概率总体上非常低。

在任何情况下，你实际的对话历史都不会被删除。你可以像任何 iMessage 聊天一样向上滚动查看整个对话。只有模型的工作上下文会被压缩。

## Grok Bot 如何变得更好

系统通过两个循环改进：

- **内循环（inner loop）** 每天运行。团队发现缺陷并修复运行框架、提示词或推理。他们会用一些评估（eval）检查这些更改，然后发布给我们。
- **外循环（outer loop）** 每月或每几个月运行一次。他们用收集到的失败案例训练新模型。

我想对于「智能体是否正确选择了快速工作还是辅助工作流」这类决策，存在某种形式的可观测性，并且这直接输入到外循环。

随着时间推移，模型会针对产品进行训练，两者一起改进。过去存在于提示词和运行框架中的经验，会被直接构建进模型本身。这也是为什么有人说你可以扔掉精心编写的 `AGENTS.md` 文件和自定义技能，因为下一个模型可能已经被训练成能自己完成这些事情。

像 SpaceXSI、OpenAI 和 Anthropic 这样的前沿实验室今天构建的许多东西，实际上是为下一代模型打基础。

这是我了解到的关于这些聊天机器人如何工作的最酷的事情之一。它们确实是围绕聊天中的人类交互来训练的。
