# 分析 Personal Agent 资料

开始前先读 [skills/repo-conventions/SKILL.md](../repo-conventions/SKILL.md)：提交推送、路径写法、本机 shell 的坑等通用约定写在那里。

这个 skill 负责笔记的「分析」一侧，与 `skills/collect-sources/` 的收集一侧分开：**素材归素材，分析归分析。** 资料页（`docs/*/sources/`）只由收集 skill 写；本 skill 只写分析页，不改资料页。

## 两个维度（用户 2026-11-12 决定）

```
content/zh-cn/
  docs/<product>/analysis/        产品维度：一个产品，覆盖所有主题
    _index.md                     产品总览：概要、定位、时间线、整体架构、主题索引、资料缺口
    <topic>/_index.md             该产品在某个主题上的分析
  analysis/                       主题维度：与 docs/ 平级
    _index.md
    <topic>/_index.md             一个主题，横向比较所有产品
```

- 主题清单、slug、各主题要回答的问题见 [references/topics.md](references/topics.md)。共 13 个主题；「行业格局」只在主题维度。
- 页面模板见 [references/page-templates.md](references/page-templates.md)。
- 进度见 [references/progress.md](references/progress.md)：开始前先读，完成后更新。
- 各产品「已读、有意不引用」的资料记在 `references/uncited/<product>.tsv`，由 `inventory.py --new` 读取（见「增量更新」）。
- **先产品，后主题**（用户 2026-11-12 决定）。产品分析直接读资料；主题分析主要读各产品的主题页，再补读 industry 资料和少量原文核对，不重读全部资料。
- 分工：产品页讲深度（这个产品怎么做、为什么、证据、问题）；主题页讲比较（对照表、分歧、共性、趋势），产品细节只写一两句并链接到产品页，不重复展开。
- 资料少的主题（一般少于 3 篇相关资料，或资料只有一句话的信息）不单独成页，在产品总览的「主题分析」表里写一两句并注明资料不足，`progress.md` 填「—」。

## 证据规则

分析页的每个事实性陈述都要能追溯到资料页。

- **引用格式**：用 Hugo 的 `relref` 链接资料页目录，例如 `[官方发布]({{< relref "/docs/muse/sources/official/2026-09-08-introducing-muse" >}})`。路径写错时 `hugo` 报 `REF_NOT_FOUND` 并构建失败，可借此校验（2026-11-12 实测，Hugo 0.121.1）。链接文字写资料的简称，不写「链接」「这里」。分析页之间互相引用也用 `relref`。
- **证据等级**：按资料所在的类型目录区分说法的来源，行文中写明：
  - 官方（`official/`）：「官方称」「帮助文档写明」。官方说法只证明厂商这样宣称，不证明实际效果。
  - 媒体（`media/`）：区分一手实测、采访披露与转述；`basedOn` 不为空的是二手报道，写「据某媒体转述某报道」。
  - 社区（`community/`）：个人实测、独立分析、用户反馈；单个用户的报告写「有用户报告」，不当作普遍现象。
  - 实测（`exploration/`）：用户自己的实测，写明测试时间与条件。
- **数字**写明出处、口径与时间点，例如「据 Meta 2026-10-29 财报会，上线约一个半月超 1000 万人设置」。不同来源的数字矛盾时并列写出，不自行取舍或换算。
- **时间**：功能、价格、开放范围会变，写「截至 YYYY-MM-DD 的资料」。较早资料的说法被后来的资料推翻时，写出变化及日期。
- **推断**与事实分段：推断单独成段，用「推断：」或「从……看，可能……」开头，写明依据哪些事实；不把推断写成事实。
- 资料回答不了的问题写进「资料缺口」，同时记入 `progress.md` 的资料缺口表。分析阶段不上网补资料；需要补的由用户安排回到收集阶段。

## 文风

- 书面中文，陈述句，不用口语和网络用语，不用第一人称（「我」「我们」「笔者」），不用感叹和反问。
- 先结论后展开：每页开头「概要」列结论，正文展开依据。
- 小节名写具体内容（如「每个用户一台云端虚拟机」），不写「背景」「分析」这类空泛标题。
- 产品名、功能名用资料中的原名；功能首次出现时可写「中文说明（English）」，与译文的做法一致。
- 对比用表格，时间线用表格；能用一句话说清的不画图。确有必要的示意图用 Mermaid 或 SVG，放在页面目录内。
- 不写营销式评价（「革命性」「王炸」）；转引原文的说法时加引号并注明出处。

## 产品维度的流程

1. **确认会话。** 一个产品一个会话（沿用收集阶段的规则）：当前会话里已做过别的产品或主题时，先提交、推送，建议用户开新会话，读本 skill 和 `progress.md` 接续。
2. **清点资料。** 运行 `python3 skills/analyze/scripts/inventory.py product <product> > <临时目录>/inv.tsv`，得到该产品资料和 industry 中涉及该产品的资料（路径、类型、日期、fidelity、translation、tags、标题）。只看统计和标题列表，不读正文。`fidelity: 仅链接` 的资料没有正文，只能引用其基本信息。
3. **按资料分组提取要点（用户 2026-11-13 确认）。** 不按主题分组：各主题的标签大量重叠，按主题分组会让同一篇资料被读三四遍。做法是：
   - 用脚本按正文大小把资料分成若干组，每组正文合计约 200–270 KB（Muse 189 篇分成 10 组，每组 11–36 篇）；单篇特别大的资料单独一组。分组清单（`inventory.py` 的行）写到临时目录。`inventory.py` 的输出没有表头，第一行就是资料，分组时不要跳过（2026-11-13 Grok Bot 分析时漏掉了第一行的发布稿，事后补派）。
   - 每组交给一个使用较便宜模型（Sonnet）的子 agent，并行运行。任务说明用 [references/extract-brief.md](references/extract-brief.md)，附上该组清单和笔记的输出路径。每篇资料只读一次，按全部主题（另加时间线、定位、资料页问题）分节写笔记；每条要点附资料路径、证据类型和不超过 40 字的原文短引。子 agent 不回传原文，只回一行路径和条数。
   - 全部完成后，用脚本核对清单中每篇资料的路径都出现在笔记里，漏掉的补派。
   - 用脚本把各组笔记按小节合并成每个主题一个文件（如 `bytopic/runtime.md`）。
4. **写主题页。** 主题笔记合计主对话读得下时，主对话自己读笔记写页面。写法（2026-11-13 WorkBuddy 分析时使用，用户确认保留）：草稿里的引用不写完整的 relref，写短宏：资料用 `[[AU]]`、`[[AU|自定义文字]]`，主题页互链用 `[[t:runtime]]`；键与资料的对照写在草稿目录的 `refs.tsv`（键、资料路径、链接文字三列，清点资料后先定好）。草稿按 `<slug>.md`、`_overview.md` 命名放在临时目录，写完用 `python3 skills/analyze/scripts/expand_drafts.py <product> <草稿目录>` 展开写入，未知的键会报错、不写文件。一个产品几百处引用，完整 relref 每处约 80 字符，短宏能省下大部分输出。读不下时（Muse 合并后约 34 万字），每个主题交给一个 fork 并行写（fork 继承本 skill 和模板等上下文），要求它：
   - 只读该主题的合并笔记，按模板写 `docs/<product>/analysis/<slug>/_index.md`。
   - 关键数字、日期、引语、媒体名用 `grep` 回资料页核对后再写；笔记里查不到出处的说法不写，并在回报中列出。笔记是子 agent 写的，会有张冠李戴（Muse 分析中出现过媒体名写错、引用了资料里没有的说法）。
   - 核对用的临时脚本和文件名带上主题名（如 `chk_runtime.py`）：并行的 fork 共用同一个临时目录，同名文件会互相覆盖。本机的 `grep` 是 ugrep，带长上下文的中文正则会超出复杂度限制，核对用 `/usr/bin/grep` 或 Python。
   - 写完只回报：页面路径、三五句主要结论、相互矛盾的说法、资料缺口、核对时发现的笔记错误。

   资料页问题另交一个 fork：读合并后的 `source-issues` 笔记，逐条回资料页核对，输出 `progress.md` 资料页问题表的行（不成立的写「无需改」及理由）。
5. **写产品总览。** 主对话根据各 fork 的回报和时间线、定位两份笔记，改写 `docs/<product>/analysis/_index.md`：时间线取自「发布」「功能更新」标签的资料，概要从各主题页的结论中提炼；上线日期、用户数、价格等总览里的关键数字由主对话自己 `grep` 核对。
6. **校验。** `npm run build` 退出码为 0（relref 全部有效）；新页面出现在侧边栏；抽查每页 3–5 个事实与资料一致。
7. **更新进度与提交。** 更新 `progress.md`（各格填 `sourcesUntil`、资料缺口、资料页问题）。运行 `inventory.py product <product> --new`，列出的是读过但页面没有用 relref 引用的资料；确认它们确实不需要引用后，加 `--record "<日期> 初次分析时已读，页面未引用"` 记入 `references/uncited/<product>.tsv`，供增量更新排除。单独提交，提交信息如 `analysis: muse 总览与 12 个主题`；推送。
8. **报告。** 向用户报告：写了哪些页、每页的主要结论（一两句）、资料不足的主题、资料缺口、需要用户判断的问题（如矛盾的说法、标签打得不准的资料）。

## 主题维度的流程

1. 确认相关产品的主题页都已完成（看 `progress.md`）；没完成的产品在报告里说明，主题页注明未覆盖。
2. 读各产品的 `<slug>/_index.md`（没有单独成页的读产品总览中对应的一两句）。
3. 用 `inventory.py tag <主要标签>` 列出资料，从中挑 industry 资料交给子 agent 提取要点，方法同产品维度第 3 步（任务说明中的小节只保留该主题）。产品页之间说法不一致或需要核对细节时，回到原始资料核对。
4. 按模板写 `analysis/<slug>/_index.md`。
5. 校验、更新进度、提交（`analysis: 主题 运行环境`）、推送、报告，同产品维度。

## 增量更新

新资料入库后：

1. `inventory.py product <product> --new` 列出未分析的资料。判断依据是引用，不是日期：没有被 `docs/<product>/analysis/` 下任何页面用 relref 引用，也不在 `references/uncited/<product>.tsv` 中的，才算未分析。不用 `--since <sourcesUntil>`，因为同一天收集的资料可能一部分已分析、一部分没有（2026-11-13 Muse 增量更新时遇到过）。
2. 读这些资料，判断影响哪些主题页，只更新受影响的页面并改 `analyzedAt`、`sourcesUntil`。
3. 再运行一次 `--new`：剩下的是读过但不需要引用的资料（内容已被其他资料覆盖、与该产品关系弱等），确认后加 `--record "<日期> 增量更新时已读，<不引用的理由>"` 记入记录文件。之后 `--new` 应为 0 篇。

`uncited/<product>.tsv` 只记「已读、有意不引用」的资料；以后页面改为引用其中某篇时，不必删记录。结论改变时，在页面相应位置写明变化与日期，不悄悄改写。产品页更新后，检查对应主题页是否需要跟着改。

## 省用量

收集阶段的四条硬性规则同样适用（见 `skills/collect-sources/SKILL.md` 的「省用量的做法」）：一个产品（或一个主题）一个会话；批量用脚本，少发小命令；资料正文交给子 agent 读，每篇只读一次，主对话只读笔记（或 fork 的回报）和少量核对段落；控制命令输出。写分析页是主要的输出开销，正文不要冗长：概要抓结论，正文给依据，不复述资料摘要。

## 不做的事

- 不修改 `docs/*/sources/` 下的资料页，不改资料的标签和摘要；发现资料页有问题（标签不准、摘要有误）时记入 `progress.md` 的「资料页问题」表并报告用户，由收集一侧处理；用户要求当场处理时，按 collect-sources 的规则改，资料页的修改单独提交。
- 判断资料页标签准不准，按整篇资料的主要内容判断，不按当前产品的相关段落判断：industry 资料多是多产品文章，与当前产品无关的标签可能仍然成立。记录前先看小节结构（`grep '^#'`）；只是与当前产品关系弱的，记成 products 依据弱，不记成标签错误（2026-11-13 Today 分析中把 Z Finance 一文的「模型」「运行环境」误记为问题，复核后全文有专门章节，用户同意不改）。
- 不在分析阶段上网检索或引入资料库以外的信息；常识性背景（如公司是谁）可以写，但不写资料库里没有出处的具体事实和数字。
- 不分析未纳入跟踪的产品；它们只在「行业格局」中作为参照提及。
- 不为了填满矩阵硬写资料不足的主题页。
- 不在 skill、任务说明、脚本里写死 home 路径，写 `$HOME/...` 或相对路径；这条和推送、shell 等通用约定见 [skills/repo-conventions/SKILL.md](../repo-conventions/SKILL.md)。
